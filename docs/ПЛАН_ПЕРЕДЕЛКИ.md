## Принципы

1. Веб-часть (`backend/app`, `frontend`) соответствует `docs/tz.md` и **не трогается**,
   кроме точек, явно указанных ниже. Все правки — в `backend/ai_module` и в новом
   пакетном входе.
2. Контракт `ai_module/interface.py` расширяется полями, но не ломается:
   backend продолжает вызывать `analyze_study(paths) -> AIStudyResult`.
3. Внутренний справочник нарушений (`violation_catalog.py`) остаётся как есть —
   он нужен UI и экспертной разметке. Наружу он отдаётся **через слой маппинга**
   на 5 официальных значений. Никогда не выводить в `violation_type` коды
   `low_image_quality`, `dicom_technical_error`, `phi_not_removed`.
4. Две точки входа, один `ai_module` под ними: веб-сервис (для защиты) и
   пакетный CLI (для сдачи таблицы).

## ШАГ 0. Блокер: связать разметку со снимками

**Делать первым, всё остальное от этого зависит.**

В `НД_для_обучения.zip` лежит `Разметка.xlsx` (лист «Калибровка», 100 строк данных,
строки 3..102; шапка двухуровневая, строки 1–2). Колонки:
- B `study` — идентификатор вида `2.25.306921081709806079165809721263236241032`
- C, D, E — Позвоночник: корректная укладка / ось выровнена (до 5°) / посторонние
  предметы, артефакты, наложения
- F, G — Проксимальный отдел **правого** бедра: позиционирование-ротация / область интереса
- H, I — то же для **левого** бедра
- J, K, L — «Итог» по каждой области, M — комментарий (встречается «сколиоз»)
- дальше формулы COUNTIF и сводка «Норма/Патология» — это статистика автора, не данные

Кодировка меток: **0 = норма, 1 = нарушение** (проверить на нескольких строках:
в строке с `1` в колонке E итог J тоже `1`).

Проблема: три несовпадающих пространства идентификаторов.
- имя папки исследования: `1.2.840.113619.2.110.512719.20250403090444`
- `StudyInstanceUID` внутри DICOM: `1.2.643.5.1.13.13.12.2.77.8252.0811...`
- `study` в xlsx: `2.25.30692...`

Порядок разбора:
1. Пройти все 100 папок, собрать из каждой полный набор DICOM-тегов (не только
   StudyInstanceUID: смотреть SOPInstanceUID, SeriesInstanceUID, AccessionNumber,
   StudyID, частные теги 0x0009/0x0019/0x7FE1, `ImageComments`).
   Искать подстроку `2.25...` где угодно в датасете тегов.
2. Если не нашлось — проверить гипотезу «порядок строк xlsx = отсортированный
   список папок» (100 = 100). Проверять не на порядке, а на содержании:
   у строк, где помечены обе области бедра, в папке должно быть ≥3 снимка;
   у строк только с позвоночником — меньше. Совпадение по 100 строкам
   подтверждает или опровергает гипотезу.
3. Если не подтвердилось — **это вопрос заказчику, задать сразу**, не тратить
   на перебор больше часа.

Результат шага: `backend/ai_module/labels.py` — функция, отдающая
`{study_dir: {'spine': {...}, 'hip_right': {...}, 'hip_left': {...}}}`,
и отчёт, сколько исследований удалось связать.

Также на шаге 0: распаковывать вложенные архивы **с указанием CP866**,
иначе пути превращаются в мусор.

## ШАГ 1. Определение анатомической области

Сейчас `heuristics.py` области не определяет вообще. Нужен классификатор
`поясничный отдел позвоночника` / `проксимальный отдел бедра`.

- Опираться **только на изображение**. Суффиксы `_ПОП/_ППОБ/_ЛПОБ` есть в «Для теста»,
  но в закрытом тесте их не будет (разъяснения, вопрос 15) — использовать их
  исключительно как валидацию классификатора на 3 тестовых файлах.
- Сторона (лево/право) в выходной таблице не нужна, но внутри различать полезно:
  разметка в xlsx ведётся по сторонам.
- Снимки маленькие (≈235–300 px по стороне), исследование = несколько снимков.
  Начать с простых признаков формы/соотношения сторон и только при неудаче —
  с маленькой CNN.

Выход: поле `anatomical_region` в `AIImageReport`.

## ШАГ 2. Калибровка геометрии

Пиксель **неквадратный**: 1,05 мм по Y, 0,6 мм по X (разъяснения, вопрос 1);
тегов `PixelSpacing`/`ImagerPixelSpacing` в файлах нет — проверено, они отсутствуют.

- Завести константы в `ai_module/calibration.py`, читать тег если он есть,
  иначе падать на константы.
- **Исправить `_tilt_from_vertical_deg`**: сейчас угол считается по пикселям, а при
  анизотропии 1,05/0,6 это даёт систематическую ошибку — критично, потому что
  порог «до 5°» из ТЗ проверяется именно им.
- Все метрические критерии ТЗ (3 см над большим вертелом, 2 см от бокового края)
  считать через эти константы.

## ШАГ 3. Маппинг нарушений на официальные значения

Создать `ai_module/submission_mapping.py`. Допустимые значения (дословно, разъяснения, вопрос 6):

Поясничный отдел позвоночника:
- `Некорректная укладка`
- `Не выравнена ось позвоночника`
- `Присутствуют посторонние предметы`

Проксимальный отдел бедра:
- `Некорректная укладка`
- `Некорректная область интереса`

Правила: несколько нарушений — через `;`. При отсутствии — **пустое поле**
(не «нет», не «—», не `None`).

Соответствие с внутренними кодами и колонками разметки:
| xlsx | область | внутренний код | violation_type |
|---|---|---|---|
| C | позвоночник | incorrect_positioning | Некорректная укладка |
| D | позвоночник | — (новый) | Не выравнена ось позвоночника |
| E | позвоночник | artifact | Присутствуют посторонние предметы |
| F/H | бедро | incorrect_positioning | Некорректная укладка |
| G/I | бедро | incomplete_field_of_view | Некорректная область интереса |

Добавить в `violation_catalog.py` код `spine_axis_misaligned` — сейчас
«не выравнена ось» отдельного кода не имеет, хотя эвристика наклона уже есть.

## ШАГ 4. Модель вместо эвристик

Главная работа недели. `heuristics.py` — классическое CV без обучения;
теперь есть ~100 размеченных исследований (499 DICOM).

- Датасет маленький → дообучение предобученной сети (ImageNet backbone),
  аугментации, кросс-валидация по **исследованиям**, не по снимкам
  (иначе утечка: снимки одного пациента попадут и в train, и в val).
- Задача многозначная: отдельные головы на каждое нарушение своей области.
- `heuristics.py` **не удалять** — оставить как fallback и как базовую линию
  для сравнения в презентации. Замена делается подменой реализации за
  `interface.analyze_study`, backend и UI не меняются.
- Если модель не успевает выйти лучше эвристик — сдаём эвристики,
  это лучше, чем недообученная сеть.

## ШАГ 5. Выходная таблица и пакетный прогон

Новый `backend/batch_predict.py`: на вход папка с DICOM, на выход таблица.

Колонки:
- `quality_class` — целое 0 / 1
- `quality_prob` — вероятность нарушения, **[0;1]** (разъяснения, вопрос 8)
- `anatomical_region` — `Поясничный отдел позвоночника` / `Проксимальный отдел бедра`
- `violation_type` — см. шаг 3

**Ловушка**: внутри `overall_score` — это 0..100 и означает *качество*.
`quality_prob` — вероятность *нарушения*. Инвертировать и нормировать,
иначе ROC-AUC сдадим перевёрнутой. Обязательно проверить на «Для теста»:
у заведомо плохого снимка `quality_prob` должна быть ближе к 1.

Проверить на 3 файлах из «Для теста», где суффиксы имён дают ожидаемую область.
