# Densito-AI — оценка качества исследований денситометрии (DXA)

Сервис искусственного интеллекта, который автоматически проверяет качество
денситометрических исследований в формате DICOM: определяет анатомическую
область, решает, пригоден ли снимок для клинической интерпретации, и называет
тип нарушения по таксономии заказчика. Сделан по ТЗ хакатона ЛЦТ 2026
(Центр диагностики и телемедицины, «Сервис ИИ по оценке качества исследований
плотности костей человека»).

```
DICOM / zip-архив ──► определение области ──► проверка критериев качества ──► таблица результатов
                     (позвоночник / бедро)    (правила ТЗ + обученные модели)   (xlsx/csv, ТЗ п.2.5)
                                                        │
                                                        └──► веб-интерфейс: просмотр снимка, находки AI,
                                                             экспертная проверка, статистика
```

## 1. Возможности и ограничения

**Что умеет**

- **Пакетная обработка** (ТЗ п.2.5, 2.7): папка, zip-архив (в т.ч. вложенные
  архивы и имена в кодировке cp866) или отдельный DICOM-файл → общая таблица
  `.xlsx`/`.csv`. Через командную строку, REST API (`POST /batch`) и страницу
  «Пакетная обработка» веб-интерфейса.
- **Отчёт DICOM SR** (ТЗ п.2.6): текстовое описание выявленных нарушений в
  стандарте DICOM (Basic Text SR) — по каждому снимку. Документ кладётся в то же
  исследование, что и снимок, и ссылается на него, поэтому PACS покажет отчёт
  рядом со снимком. Выгружается из карточки исследования, из пакетной обработки
  zip-архивом вместе с таблицей (ТЗ п.2.7) и из командной строки (`--sr`).
- **Определение анатомической области** только по пикселям (без имён файлов
  и тегов): поясничный отдел позвоночника / проксимальный отдел бедра.
- **Классификация качества**: `quality_class` (0 — качественное, 1 — есть
  нарушение) и вероятность нарушения `quality_prob` ∈ [0; 1].
- **Типы нарушений** — дословно по «Разъяснениям по вопросам ЛЦТ_V2», несколько
  нарушений через `;`:
  - позвоночник: «Некорректная укладка», «Не выравнена ось позвоночника»,
    «Присутствуют посторонние предметы»;
  - бедро: «Некорректная укладка», «Некорректная область интереса».
- **Веб-интерфейс** (ТЗ п.2.6): загрузка DICOM/zip, собственный DICOM-вьюер
  (масштаб, яркость/контраст, находки поверх снимка), результат AI с
  объяснением, экспертная проверка (подтвердить/отклонить/исправить находку,
  добавить свою), пакетная обработка архива с выгрузкой таблицы и SR,
  роли admin/expert, журнал действий, статистика.
- **Работает локально**: инференс без обращения к внешним сервисам, медицинские
  изображения никуда не передаются. Интернет нужен только при сборке образов.

**Ограничения** (подробно — [раздел 10](#10-известные-ошибки-ограничения-и-их-обработка))

- Обучено и проверено на данных **одного аппарата** (100 исследований,
  499 снимков, пиксель 1,05 × 0,6 мм). Другой аппарат или другой кроп
  потребует проверки и, вероятно, переобучения.
- **«Некорректная область интереса» бедра** в разметке встречается 1 раз —
  проверка реализована правилом, но её качество оценить нечем (F1 = 0).
- **Проекция** исследования (ТЗ п.2.2) не определяется — в выходной таблице
  для неё нет колонки.
- Выборка маленькая, поэтому доверительные интервалы метрик широкие.

## 2. Быстрый старт

Нужен Linux (или другая UNIX-подобная система) с Docker Engine и плагином
Docker Compose.

```bash
git clone https://github.com/ASKentr/densito-ai.git densito-ai
cd densito-ai
./run.sh up
```

- веб-интерфейс: <http://localhost:5173> (логины `admin` / `admin12345` и `expert` / `expert12345`)
- API и Swagger: <http://localhost:8000/docs>

Пакетная обработка тестового набора — таблица результатов по ТЗ:

```bash
./run.sh batch /путь/к/test_set.zip results.xlsx
```

Первая сборка скачивает ~550 МБ (базовые образы, PyTorch и другие пакеты) и
занимает несколько минут; следующие запуски — секунды.

организатора); пути к нему передаются скриптам обучения и оценки явно.

## 4. Системные требования и зависимости

Инференс идёт **на CPU**, GPU не требуется (если он есть — не используется и
не мешает). Замеры на ноутбуке Intel Core i5-1145G7 (4 ядра / 8 потоков,
16 ГБ ОЗУ): пакетная обработка 100 исследований (499 файлов) — 29,5 с вместе
с загрузкой модели; **0,15 с на исследование** в среднем, 0,9 с максимум
(ТЗ п.2.7 — не более 3 минут); пиковая память процесса — **411 МБ**.

| | Минимальная | Рекомендуемая |
|---|---|---|
| Процессор | x86-64, 2 ядра | x86-64, 4 ядра и больше |
| Оперативная память | 2 ГБ | 4 ГБ |
| Диск | 5 ГБ (образы ~2 ГБ + кэш сборки) | 10 ГБ + место под загружаемые исследования |
| GPU | не требуется | не требуется |
| ПО | Linux, Docker Engine 24+, Docker Compose v2 | то же |
| Сеть | интернет только на время сборки | то же |

**Зависимости** (все версии зафиксированы, ТЗ п.3.2):

- базовые образы: `python:3.11.16-slim-bookworm`, `node:22.23.2-alpine3.24`,
  `nginx:1.31.6-alpine3.24` — по версии и digest;
- Python: FastAPI 0.115, SQLModel 0.0.22, pydicom 2.4.4, NumPy 1.26.4,
  SciPy 1.13.1, OpenCV 4.10 (headless), PyTorch 2.14.0 (CPU), torchvision 0.29.0,
  openpyxl 3.1.5 и др. — полный список с транзитивными в `backend/requirements.lock`;
- frontend: React 19, React Router 7, dicom-parser, Vite 8 — версии в
  `frontend/package-lock.json` (`npm ci`).

## 5. Сборка и запуск

### Docker (основной способ)

```bash
./run.sh up          # собрать и запустить (при первом запуске создаётся .env со случайным SECRET_KEY)
./run.sh status      # состояние контейнеров
./run.sh logs        # журналы
./run.sh down        # остановить (данные сохраняются в томах Docker)
./run.sh reset       # остановить и удалить данные
./run.sh batch <папка|архив.zip|файл.dcm> <результат.xlsx|.csv> [--sr]   # --sr: ещё отчёты DICOM SR в sr/ рядом с таблицей
```

Если сервис открывают не с той же машины, задайте её адрес при первом
запуске: `PUBLIC_HOST=10.0.0.5 ./run.sh up`. Пароли демо-учёток, порты и адреса —
в файле `.env` (см. [docs/РАЗВЁРТЫВАНИЕ.md](docs/РАЗВЁРТЫВАНИЕ.md)).

Без скрипта: `docker compose up -d --build`; пакетная обработка —
`docker compose run --rm -v /путь/к/данным:/input backend python batch_predict.py /input/test_set.zip /input/results.xlsx`.

### Без Docker (для разработки)

```bash
# backend (Python 3.11+)
cd backend
pip install -r requirements-model.txt -c requirements.lock
python -m uvicorn app.main:app --port 8000
python batch_predict.py <вход> <результат.xlsx> [--sr папка_для_SR]

# frontend (Node 20.19+ / 22.12+), в отдельном терминале
cd frontend
npm ci
npm run dev          # http://localhost:5173
```

При первом старте backend создаёт БД SQLite, справочник нарушений и
демо-учётки `admin` / `expert` (пароли — переменные `BOOTSTRAP_ADMIN_PASSWORD`,
`BOOTSTRAP_EXPERT_PASSWORD`).

## 6. API

Интерактивная документация — `http://<хост>:8000/docs` (Swagger). Все методы,
кроме `/auth/login` и `/health`, требуют заголовок `Authorization: Bearer <token>`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/login` | вход (form: `username`, `password`) → JWT |
| GET | `/auth/me` | текущий пользователь |
| **POST** | **`/batch?format=xlsx\|csv[&sr=true]`** | **пакетная обработка: zip или DICOM → таблица результатов (ТЗ п.3.2); с `sr=true` — zip: таблица + отчёты DICOM SR** |
| POST | `/studies/upload` | загрузить исследование (DICOM или zip) в веб-интерфейс |
| GET | `/studies` | список исследований с фильтрами |
| GET | `/studies/{id}` | карточка исследования: снимки, результат AI, находки |
| POST | `/studies/{id}/analyze` | запустить AI-анализ |
| GET | `/studies/{id}/images/{image_id}/preview`, `/raw` | превью PNG / исходный DICOM |
| GET | `/studies/{id}/images/{image_id}/sr` | отчёт DICOM SR по снимку с учётом экспертной проверки (ТЗ п.2.6) |
| PATCH | `/findings/{id}` | экспертная проверка находки (подтвердить/отклонить/изменить) |
| POST | `/studies/{id}/findings` | добавить находку эксперта |
| POST | `/studies/{id}/complete_review` | завершить экспертную проверку |
| GET/POST/PATCH/DELETE | `/admin/violation-types`, `/admin/users`, `/admin/audit-log`, `/admin/stats` | администрирование (роль admin) |
| GET | `/health` | проверка работоспособности и самопроверка ИИ-модуля: `status` = `ok` / `degraded`, в `ai` — готовность, версия модели и состояние каждой части (правила, модели позвоночника, нейросеть). Без авторизации; его показывает индикатор в шапке веб-интерфейса |

Пакетная обработка через API:

```bash
TOKEN=$(curl -s -X POST http://localhost:8000/auth/login -d "username=expert&password=expert12345" \
        | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
curl -X POST "http://localhost:8000/batch?format=xlsx" -H "Authorization: Bearer $TOKEN" \
     -F "file=@test_set.zip" -o results.xlsx
```

В заголовках ответа — `X-Processed-Files` и `X-Failed-Files`. Таблица вместе
с отчётами DICOM SR — тот же запрос с `&sr=true` и `-o results.zip`.

## 7. Форматы входных и выходных данных

**Вход** — DICOM-исследования без разметки (ТЗ п.2.4):

- папка (поиск рекурсивный), zip-архив (вложенные zip раскрываются, имена в
  cp866 декодируются) или один файл;
- DICOM распознаётся по расширению `.dcm`/`.dicom` или по сигнатуре `DICM`
  (файлы без расширения тоже находятся); прочие файлы (`.txt`, `.xlsx`,
  `__MACOSX`) пропускаются;
- персональные данные не нужны: решение от них не зависит (теги PHI
  проверяются только для предупреждения в веб-интерфейсе).

**Выход** — таблица `.xlsx` или `.csv` (UTF-8 с BOM), одна строка = одно
изображение (ТЗ п.2.5):

| Колонка | Формат | Значение |
|---|---|---|
| `path_to_study` | String | путь к файлу (для zip — `<архив>/<путь внутри>`) |
| `study_uid` | String | StudyInstanceUID из DICOM |
| `image_uid` | String | SOPInstanceUID из DICOM |
| `anatomical_region` | String | «Поясничный отдел позвоночника» или «Проксимальный отдел бедра» |
| `quality_class` | Integer | 0 — качественное, 1 — есть нарушение |
| `quality_prob` | Float | вероятность нарушения ∈ [0; 1] (доп. колонка, разрешена в «Разъяснениях», вопрос 8) |
| `violation_type` | String | нарушения через `;`, пусто — если нарушений нет |
| `processing_status` | String | `Success` / `Failure` |
| `time_of_processing` | Float | время обработки файла, с |

`quality_class = 1` тогда и только тогда, когда `violation_type` не пуст.
Если файл не удалось обработать, строка получает `Failure` с пустыми
результатами, а причина пишется в `<результат>.errors.csv` рядом с таблицей.

**Отчёт DICOM SR** (по запросу: `--sr`, `sr=true` или кнопка в карточке) —
файл `<путь снимка>.sr.dcm` на каждый успешно обработанный снимок:

- Basic Text SR (SOP Class `1.2.840.10008.5.1.4.1.1.88.11`), кодировка UTF-8;
- тот же `StudyInstanceUID`, что у снимка, отдельная серия `Modality = SR`,
  ссылка на исходный снимок (`IMAGE` + `CurrentRequestedProcedureEvidenceSequence`);
- содержимое: алгоритм и версия модели, анатомическая область, заключение
  («Качественное исследование» / «Есть нарушение качества»), вероятность,
  каждое нарушение с пояснением алгоритма, статус экспертной проверки (из
  карточки), примечание о том, что это не диагноз;
- UID документа выводится из UID снимка и содержимого — повторный прогон на
  тех же данных даёт тот же UID (ТЗ п.2.7, воспроизводимость).

## 8. Модель, предобработка и постобработка

Решение — **гибрид**: для каждого нарушения используется метод, который
лучше всего показал себя на кросс-валидации с доверительными интервалами.
Подробное обоснование — [docs/ГИБРИД_МОДЕЛЬ.md](docs/ГИБРИД_МОДЕЛЬ.md).

**Предобработка** (общая):
1. чтение DICOM (pydicom), RescaleSlope/Intercept;
2. окно яркости по перцентилям 1–99 % → 8 бит (не зависит от тегов окна);
3. сегментация кости: порог Otsu + крупнейшая связная компонента → маска и
   рамка объекта;
4. размер пикселя: теги PixelSpacing, при их отсутствии — 1,05 мм (Y) × 0,6 мм (X)
   по «Разъяснениям» (все углы и расстояния считаются в миллиметрах).

**Анатомическая область** — по билатеральной симметрии маски (позвоночник
симметричен, бедро — нет), две оси отражения: центр кадра и центр масс
объекта; порог 0,30.

**Поясничный отдел позвоночника**
- *Не выравнена ось*: наклон главной оси маски (PCA) в мм > 5° — критерий ТЗ.
- *Некорректная укладка*, *посторонние предметы*, общая вероятность
  нарушения: три логистические регрессии на 4 признаках, выбранных по
  критериям ТЗ (яркость нижних углов кадра — гребни подвздошных костей;
  верхние углы и ширина верхней полосы — Th12 и инородные предметы).
  Порог флага — доля помеченных = доля нарушений в обучении.

**Проксимальный отдел бедра**
- *Некорректная укладка* (позиционирование и ротация): свёрточная сеть
  ResNet18 (инициализация ImageNet, слои 1–2 заморожены), вход — кроп объекта
  с отступом 12 %, 160 × 160, две головы (позвоночник/бедро). Обучение:
  12 эпох, Adam, lr 1e-4, аугментации (горизонтальное отражение, поворот ±6°,
  яркость/контраст), взвешенная функция потерь против дисбаланса классов.
  Порог 0,2735 — доля помеченных = доля нарушений (квантиль OOF-вероятностей).
- *Некорректная область интереса*: кость касается бокового края кадра
  (≤ 2 пикселя).

**Постобработка**: внутренние коды нарушений → дословные формулировки
заказчика (`submission_mapping.py`), объединение через `;`; `quality_class` —
наличие хотя бы одного нарушения; `quality_prob` — для позвоночника
вероятность из обученной модели, для бедра — вероятностное «ИЛИ» CNN и
правила области интереса.

**Данные и разбиение**: 100 исследований / 499 снимков с экспертной
разметкой на уровне исследования. Кросс-валидация — 5 фолдов **по
исследованиям** (снимки одного пациента не попадают одновременно в обучение
и проверку). Процедура обучения и дообучения — [docs/ОБУЧЕНИЕ_МОДЕЛИ.md](docs/ОБУЧЕНИЕ_МОДЕЛИ.md).

## 10. Известные ошибки, ограничения и их обработка

| Ситуация | Что происходит |
|---|---|
| Файл не DICOM / повреждён / без пиксельных данных | строка `Failure`, пустые результаты, причина — в `<результат>.errors.csv`; пакет продолжает обработку (ТЗ п.2.7) |
| ИИ-модуль не загрузился (нет весов, ошибка PyTorch) | `GET /health` → `status: degraded` с причиной по каждой части; в веб-интерфейсе красный индикатор «ИИ-модуль недоступен», кнопки анализа неактивны; веса — `backend/ai_module/weights/` |
| Не удалось выделить кость или определить область | `Failure` с объяснением (а не «качественное» по умолчанию) |
| Нет тегов PixelSpacing | используются размеры пикселя из «Разъяснений» (1,05 × 0,6 мм) |
| Снимок другого размера/аппарата | скореры позвоночника применяются только к кадрам 150–400 px (домен обучения), иначе — правила без обучения; качество на другом аппарате не проверялось |
| «Некорректная область интереса» бедра | 1 пример в разметке — правило консервативное, ~3 % ложных срабатываний, F1 = 0 |
| Сторона бедра | не определяется (в таблице не требуется); при обучении снимки с разной оценкой правого и левого бедра исключались |
| Проекция исследования | не определяется (в выходной таблице ТЗ для неё нет колонки) |
| Страница Swagger `/docs` без интернета | оформление грузится с публичного CDN — без сети страница пустая, сам API работает |
| Системные пакеты `libgl1`, `libglib2.0-0` в образе | ставятся из репозитория Debian при сборке, версии не закреплены (остальное закреплено) |
